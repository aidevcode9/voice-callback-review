03 / Implemented evaluation workflow · F-011

One command produces an inspectable browser report

The command coordinates reusable modules through one packaged workflow. The existing evaluator remains the inference and scoring artifact writer. Saved-run inspection and baseline comparison start no inference or telemetry.

voice-callback evaluate --model qwen35-4b voice-callback evaluate --model qwen35-4b --baseline reports/text/BASELINE_ID
  1. 01

    Prepare

    Verify committed source and explicit model. Resolve optional development tracing from root .env and overrides.

  2. 02

    Infer

    Send development ID/text inputs through the shared local classifier. Expected answers stay outside requests.

  3. 03

    Persist

    Save each prediction or failure before progress advances. Preserve partial work on interruption.

  4. 04

    Score

    Close predictions, then open separate development answers. Count outcomes, failures, unsafe misses, and denominators.

  5. 05

    Review

    Validate saved artifacts and compare an explicitly selected compatible baseline. Show fixes, regressions, and configuration changes.

  6. 06

    Open report

    Read the terminal summary and local HTML with every case, transcript, expected label, decision, and evidence.

Inspect existing runs · no model call
voice-callback evaluations voice-callback evaluations --run-dir reports/text/RUN_ID voice-callback evaluations --run-dir reports/text/RUN_ID --baseline reports/text/BASELINE_ID

Any compatible completed development run can be selected as a baseline. Matching data, case coverage, scorer, and metric definitions are required; model, prompt, and source identities can differ. There is no automatic default-baseline promotion.

What the gates actually check
  • Code correctness and typesRuff correctness/import rules and formatting; Pyright strict on application source, standard on scripts and tests.
  • Behavior and reproducibilityUnittest with branch-coverage reporting, frozen-data hashes, golden input/answer separation, and candidate packet integrity.
  • Documentation and package integrityMarkdown links, feature lifecycle, quality configuration, CI structure, and isolated wheel installation. Local Pydantic checks verify pinned runtime wheels offline by hash.
  • Source-of-truth checksThe runner validates the selected index or HEAD snapshot independently of unstaged files. Missing dependencies and failed commands block the check.
Configured CI is not mandatory merge protection.The earlier PR #1 run is historical hosted evidence. This map does not assert the current branch-protection configuration or a hosted result for another revision. The project requires feature-branch review; repository enforcement must be verified separately. A green run verifies only its recorded remote revision.
05 / Standing rules and evidence

How we keep changes reviewable

  • Model output is not authorization.Agents can recommend implementation; policy checks and named human decisions govern acceptance, publishing and release.
  • Evidence belongs to a precise revision.Requirements, feature plans, Git snapshots, model/prompt/data versions, and evaluation inputs must be distinguishable.
  • Expected answers stay out of inference requests.The runner reads ID and transcript inputs, then closes predictions before the scorer opens expected answers. Approved development and held-out splits remain separate.
  • Failed stages remain failed.A type error, broken link, changed gold artifact or bad wheel blocks readiness; a model or integration failure cannot be relabeled as a successful business outcome.
  • Implementation and live verification have separate status.The text pipeline, Review desk, and coherent evaluation workflow are implemented. SRC-026 accepts F-004 text testing and QA. Current v2 development evidence exists; actual candidate freeze, real held-out measurement, numeric production targets, and audio remain follow-up work.
